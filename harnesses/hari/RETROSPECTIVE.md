# Hari retrospective

Keep only reusable maintainer lessons for `harnesses/hari` here. Current behavior
belongs in the [README](README.md), [usage guide](docs/usage.md), and
[operating model](design/harness-operating-model.md).

- Inspect existing Pi and workspace behavior before adding a parallel mechanism.
  Reuse an adequate seam and keep ownership boundaries explicit. Keep generic
  workspace guidance separate from role-specific prompt additions.
- Separate implemented behavior, observed validation, and optional design ideas.
  A scenario or proposal is not runtime evidence.
- Preserve manager-owned acceptance. Do not replace it with routine central review
  or a mandatory delegation hierarchy.
- Refresh current records and source state at consequential boundaries. Hari's
  native history and memory are useful context, not current authority. Freshness
  does not require rewriting the system prefix or repeating snapshots. Cached
  irrelevant content still consumes context and attention.
- Keep Hari's Prime Radiant knowledge small and single-writer. Prefer references
  to durable evidence over copied status narratives. Do not mistake generic harness
  resources for Hari's private memory.
- Remove guidance that no longer earns its context. Verify actual paths and links
  before deletion rather than preserving archives by default.
